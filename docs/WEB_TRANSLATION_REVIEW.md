# 웹 번역 구현: 파모에게 전달할 리뷰 자료

> 이 문서는 아래 날짜·커밋의 기록이다. 이후 개발 브랜치에서 진행한 공통 DOM 정책 분리와
> 실제 브라우저 E2E 검증은 [2026-08-28 리팩터링 기록](WEB_TRANSLATION_DOM_REFACTOR.md)을 참조한다.

확인일: 2026-08-27. 구현 기준: `d3e1a81`, 브라우저 확장 `0.7.4`, Windows 앱 `0.7.2-beta`.
이 문서는 현재 구현을 설명하고 검토 질문을 정리한 자료다. 아래 개선 검토 항목은 아직 구현한 기능이나 확정한 변경 방향이 아니다.

## 1. 먼저 전달할 요약

만들고 싶은 건 **웹사이트에서 번역을 켜면, 읽을 수 있는 글이 자연스럽게 번역되고 사이트 기능은 그대로 동작하는 경험**이야.

현재 구현은 **브라우저 확장이 웹페이지 DOM에서 텍스트를 골라서, PC에 설치된 번역 앱으로 보내고, 받은 번역문으로 원래 텍스트 노드만 바꾸는 방식**이야. 웹사이트를 서버에서 다시 만들어 보여주는 방식은 아니고, 화면 전체를 OCR하는 방식도 아니야.

확장은 Chrome·Whale·Firefox용 Manifest V3이고, 프론트는 React나 Vue 없이 순수 JavaScript·HTML·CSS를 써. 번역 앱은 Tauri 2 + Rust이고, 기본 번역은 llama.cpp + Hy-MT2 GGUF 모델로 PC 안에서 처리해. 선택하면 외부 번역기도 사용할 수 있어.

사이트마다 처음부터 따로 만드는 구조는 아니야. 범용 수집기가 제목·문단·목록·표 등을 찾고, `div`·`span`으로 만든 본문도 보완해서 읽어. 다만 입력 폼·메뉴·대화상자·코드·가격 같은 영역을 기본적으로 제외하고, 일부 사이트에는 CSS 선택자로 허용 범위를 보완하는 전용 어댑터가 있어.

지금 힘든 부분은 **읽고 싶은 문구가 메뉴·버튼·폼·팝업 안에 있거나, 나중에 표시되거나, 특이한 DOM 구조로 만들어져 있을 때 누락되는 것**이야. 예를 들어 카드 검색의 고정 라벨은 번역하고 싶은데 사용자 입력값은 건드리면 안 되고, 접힌 메뉴는 펼친 다음 처리해야 하거든. 이걸 사이트별 예외로 계속 추가하는 중이야.

리뷰받고 싶은 핵심은 **범용 텍스트 수집과 제외 정책을 어떻게 나누면 사이트별 예외를 줄일 수 있을지**, 그리고 **DOM을 보존하면서 번역문을 적용하는 현재 방식이 동적 웹페이지에도 적절한지**야. “모든 사이트 완벽 지원”보다 먼저, 일반 본문·공개 UI·이미지·iframe의 지원 범위를 어디까지 잡아야 할지도 같이 보고 싶어.

## 2. 기술 스택과 담당 역할

| 구간 | 실제 사용 기술 | 역할 |
|---|---|---|
| 확장 및 팝업 | Manifest V3, JavaScript, HTML, CSS | 페이지 수집, 토글, 목표 언어 선택, 번역문 적용 |
| 확장 백그라운드 | Chromium service worker / Firefox background scripts | 탭 상태, 페이지 연결 복구, 앱 통신 중계 |
| DOM 처리 | CSS selectors, TreeWalker, WeakMap/WeakSet | 번역할 노드와 문단 식별, 원문·번역문·노드 상태 추적 |
| 동적 화면 처리 | MutationObserver, IntersectionObserver, requestAnimationFrame | 변경 감지, 화면 근처 우선 처리, 번역문 적용 시점 조절 |
| 확장 → PC | Native Messaging, JSON | 브라우저가 등록된 네이티브 호스트와 통신 |
| PC 앱 | Tauri 2, Rust; 설정 화면은 HTML/CSS/JavaScript | 모델과 설정 관리, 요청 검증, 번역 작업 실행 |
| 호스트 → 실행 중인 앱 | 인증된 `127.0.0.1` TCP 연결 | 임의 포트와 실행마다 생성하는 토큰으로 로컬 중계 |
| 로컬 번역 | llama.cpp, GGUF; 기본 Hy-MT2 1.8B | 사용자 PC에서 추론. Hy-MT2 7B 및 실험용 TranslateGemma 4B도 선택 가능 |
| 외부 번역 옵션 | DeepL, ChatGPT·Claude·Gemini 공급자 연결 | 선택한 경우 추출 텍스트를 외부 공급자에게 전달 |
| 캐시 | 메모리, SQLite | 번역 결과 재사용; 엔진·목표 언어·프롬프트 버전 등으로 분리 |
| 테스트 | Node.js `node:test`, jsdom, Rust 테스트 | 수집·제외·복원·탭 상태·통신·번역 경로 회귀 검사 |

웹 기능은 Discord 실행 여부와 독립적으로 쓸 수 있다. Discord와 모델 런타임·표시 번역 워커는 공유하지만, 웹 문맥과 수집 상태는 별도로 관리한다.

## 3. 페이지 하나가 번역되는 과정

```text
사용자가 F4 또는 확장 팝업으로 번역 활성화
  → 사이트 정책과 전용/범용 어댑터 선택
  → 후보 문단 탐색 + 보호 영역 제외
  → 화면 근처의 텍스트 노드를 문단별로 묶어 대기열에 추가
  → 확장 백그라운드 → Native Messaging 호스트
  → 인증된 로컬 연결 → 실행 중인 Tauri/Rust 앱
  → 웹 문맥·언어 판별 → 번역 서비스와 캐시
  → 노드 ID별 결과 수신
  → 아직 유효한 원래 Text 노드의 nodeValue만 변경
```

일반 사이트는 기본적으로 직접 켜야 수집을 시작한다. 사이트 자동 번역 설정이나 현재 탭에서 명시적으로 선택한 상태가 있으면 그 정책을 적용한다.

### 수집과 제외

- 범용 어댑터는 `h1~h6`, `p`, `li`, `blockquote`, `figcaption`, `dt/dd`, `summary`, `th/td` 등을 문단 후보로 삼는다.
- 의미 있는 태그로 작성하지 않은 본문은 TreeWalker로 보완한다. 직접 텍스트와 링크·강조·줄바꿈이 섞인 `div` 기반 설명도 처리한다. 이미 찾은 문단의 인라인 요소를 독립 문단으로 중복 수집하지 않도록 제한한다.
- 공통 제외 규칙은 입력·편집 영역, 코드, 숨김, `translate="no"`, `.notranslate`, 가격·쿠키 관련 표식 등을 검사한다. 메뉴·폼·대화상자 등의 일반 제외와, 예외 어댑터도 우회할 수 없는 보호 제외를 분리한다.
- 전용 어댑터에는 `blocks`, `excludes`, `exclusionBypassBlocks`, `publicUiBlocks`, `publicForms`, `visibilityRoots` 같은 설정이 있다. 필요한 사이트에만 공개 UI 예외와 추가 감시 범위를 지정한다.
- 민감 경로 차단은 URL 경로·호스트 규칙과 사이트별 정책으로 구현한다. 이것이 임의 사이트의 모든 개인정보를 의미적으로 판별한다는 뜻은 아니다.

### 전송과 번역 단위

- 각 텍스트에 `id`, `blockId`, `text`를 붙여 보낸다. DOM 요소나 전체 HTML을 모델에 보내는 구조가 아니다.
- 보통 같은 문단의 인라인 노드를 같은 요청에 유지한다. 엔진은 문단 키로 언어 판별을 보완하고, 인접한 웹 항목을 짧은 공통 문맥으로 묶어 처리할 수 있다.
- 프로토콜의 상한은 요청당 32개 항목, 항목당 4,000자, 전체 32,000자다. 실제 대기열 배치는 처리 모드와 로컬/외부 번역기에 따라 더 작을 수 있다.
- 문단 전체가 요청 한도를 넘으면 기존 노드 경계에서 여러 요청으로 나눈다. 단, **하나의 Text 노드 자체가 4,000자를 넘으면 현재 수집기가 제외한다.** 이 둘은 다른 경우다.
- 긴 로컬 웹 번역은 짧은 추론 조각으로 나누고 사이에 양보 시간을 둔다. 외부 번역에는 페이지별 전송 문자 보호 한도가 있다.
- Native Messaging 연결은 재사용한다. 문단마다 호스트 프로세스를 새로 띄우는 구조가 아니다.

### 적용과 복원

- 부모의 `innerHTML` 또는 `textContent`를 통째로 교체하지 않는다. 기존 링크·강조 요소를 남기고 Text 노드의 `nodeValue`만 바꾼다.
- 원문과 완료된 번역문을 기억해 OFF에서는 원문으로, ON에서는 유효한 번역문으로 즉시 되돌릴 수 있다.
- 적용 직전에 노드 연결 상태, 요청 ID, 페이지 세대(`pageEpoch`), 현재 값이 저장한 원문과 같은지 확인한다. 페이지가 바뀌거나 사이트가 내용을 바꿨다면 이전 결과를 그대로 덮어쓰지 않는다.
- DOM 구조 보존이 픽셀 단위 레이아웃 보존을 보장하는 것은 아니다. 번역 길이에 따라 줄바꿈과 높이는 달라질 수 있다.

### 동적 페이지와 성능

- MutationObserver로 노드 추가·텍스트 변경·`hidden/aria-hidden/open` 변경을 본다. 번역기 자신의 쓰기는 다시 번역하지 않도록 구분한다.
- `class/style` 변화 감시는 모든 요소가 아니라 전용 어댑터의 `visibilityRoots`에 제한한다. 메뉴 상호작용도 재탐색 계기로 사용한다.
- IntersectionObserver로 화면 주변 약 120~240px의 후보를 우선 처리한다. 최초/변경 범위에서는 후보를 탐색하지만 스크롤마다 전체 문서를 재탐색하지는 않는다.
- 처리 모드에 따라 약 140~700ms 동안 요청을 모으며, 스크롤 중 DOM 적용은 미룬다. 번역문 적용은 한 프레임에 최대 두 문단 묶음으로 제한한다.
- SPA 주소 변경은 DOM 변경 처리 시점과 500ms 주기 URL 검사로 감지한다. 페이지 이동 시 이전 대기열·문맥·노드 기록을 정리한다.

## 4. 사이트별 예외가 늘어나는 지점

아래는 현재 코드와 요구 경험을 비교한 해석이다. 각 문제가 모든 사이트에서 발생한다고 실측한 결과는 아니다.

| 상황 | 현재 구조에서 예외가 필요한 이유 |
|---|---|
| 본문처럼 보이지만 메뉴·버튼 안에 있는 문구 | 일반 제외 규칙에 걸리므로 공개 UI라는 추가 근거가 필요하다. |
| 검색 폼 안의 고정 라벨 | 입력값은 보호하면서 라벨만 허용해야 해서 폼/요소 범위를 구별한다. |
| 접었다 펴는 메뉴 | DOM이 추가되지 않고 CSS만 바뀔 수 있다. 현재 CSS 변화 감시는 사이트별 범위에 의존한다. |
| X 기사처럼 대화상자에 표시되는 공개 본문 | 대화상자 기본 제외와 공개 기사 허용이 충돌하므로 좁은 예외가 필요하다. |
| 사이트가 클래스나 컴포넌트 구조를 바꿈 | 특정 CSS 선택자에 의존한 어댑터가 더 이상 맞지 않을 수 있다. |
| React/Vue 등으로 화면 내용을 계속 교체함 | 노드 유효성 검사로 오래된 결과를 버려도, 사이트의 재렌더링이 번역을 다시 지울 가능성은 남는다. 실제 프레임워크별 검증이 필요하다. |
| 번역 결과가 너무 길거나 인라인 노드별 어순이 맞지 않음 | 원래 노드와 링크를 유지하는 정책과 목표 언어의 자연스러운 어순·폭 사이에 제약이 있다. |

실제 예외 사례는 TAKARA TOMY 카드 검색 라벨·검색 탭·하단 아코디언, ShoPro 헤더 메뉴, DLsite 공개 상단 문구, X 기사와 미디어 뷰어 등이다.

따라서 “범용 처리가 아예 없어서 사이트마다 구현한다”는 설명은 부정확하다. **범용 처리 위에 보수적인 제외 정책과 사이트별 UI 허용 규칙이 겹쳐 있고, 원하는 번역 범위가 본문에서 공개 UI까지 넓어지면서 예외가 늘어나는 상태**에 가깝다.

## 5. 현재 범위 밖이거나 별도 검토할 영역

| 영역 | 현재 상태 |
|---|---|
| 카드 그림·배너 등 이미지 안의 글자 | 웹 확장 경로에서는 OCR하지 않는다. 본체의 Discord 이미지 OCR 기능과 구별해야 한다. |
| canvas·SVG·PDF·브라우저 내부 화면 | 일반 DOM 본문 번역 대상으로 처리하지 않는다. |
| 일반 iframe 문서 | 기본 콘텐츠 스크립트는 최상위 문서만 처리한다. YouTube 임베드의 보이는 제목만 제한된 별도 예외다. |
| Shadow DOM 내부 | 현재 수집 코드에는 shadow root를 재귀 탐색하는 경로가 없다. 지원을 가정하면 안 된다. |
| `title`, `alt`, `placeholder` 같은 속성 문자열 | 일반 수집 경로는 Text 노드 중심이며 속성 번역을 구현하지 않는다. |
| 한 글자 / 매우 긴 단일 노드 | 공백 제거 후 길이 2 미만 또는 JS 문자열 길이 4,000 초과인 Text 노드는 제외한다. |
| 개인정보 식별 | 경로·선택자·설정 기반 필터다. 공개 본문처럼 배치된 민감 정보까지 완벽히 식별한다고 보장할 수 없다. |

## 6. 파모에게 부탁할 리뷰 질문

1. **지원 범위를 먼저 나누는 게 맞을까?** 일반 본문, 공개 메뉴·고정 라벨, 이미지·임베드를 별도 범위로 정하면 “페이지 전체 번역”이라는 기대를 더 명확하게 설명할 수 있을까?
2. **범용 수집과 제외 정책의 경계가 적절할까?** 문단 탐색은 범용으로 유지하고, 전용 어댑터는 동적인 서비스 UI에만 제한할 수 있을까? 현재 `nav/form/dialog` 제외가 지나치게 넓은지 보고 싶다.
3. **사이트 이름보다 UI 패턴을 기준으로 공통화할 수 있을까?** 펼침 메뉴, 고정 검색 라벨, 읽기 전용 모달처럼 반복되는 패턴의 허용·가시성 처리를 공유할 수 있을까? 입력값이나 숨긴 텍스트를 전송하는 회귀는 막아야 한다.
4. **Text 노드 직접 변경이 동적 웹 앱에도 적합할까?** 노드 보존·원문 복원이라는 장점을 유지하면서 프레임워크 재렌더링과 충돌하는지 확인하고 싶다. 번역문 병기·별도 읽기 화면 등은 검토 후보이며 현재 구현은 아니다.
5. **문단 문맥과 인라인 노드 보존 방식이 적절할까?** 링크가 많은 문장의 어순, 단일 초장문 노드, 번역 길이 증가를 어떤 정책으로 다루는 게 나을까?
6. **누락 원인부터 관찰 가능하게 만들면 어떨까?** 후보 미발견, 정책 제외, 화면 밖, 미지원 DOM, 번역 실패를 구분하는 진단이 있으면 선택자 추가 전에 원인을 알 수 있을까? 현재 콘솔 진단은 있지만 이 분류 전체를 보여주는 도구는 없다.
7. **실브라우저 회귀 검증을 어떻게 구성할까?** 정적 문서, div 기반 본문, SPA/가상 목록, CSS 메뉴, 폼 라벨, 긴 문단, 링크 혼합, iframe/Shadow DOM을 대표 사례로 묶고, 번역률뿐 아니라 오수집·복원·동작 보존을 함께 확인하고 싶다.

## 8. 검증의 의미와 한계

이번 문서 작성 시 `npm run test:extension`을 실행해 228개 통과, 실패 0개를 확인했다. 문서의 상대 링크 14개, 버전 표기, 코드 블록 구분과 공백도 검사했다. 실행 코드는 변경하지 않았다.

Rust 쪽 관련 명령은 `cargo test --manifest-path src-tauri/Cargo.toml browser_translation`과 `cargo test --manifest-path src-tauri/Cargo.toml browser_bridge::tests`다. 이번 문서 작업에서 이 Rust 테스트 명령을 추가 실행하지는 않았다.

DOM 테스트는 jsdom에서 실제 콘텐츠 스크립트를 실행하지만, 요소의 위치·IntersectionObserver·번역 응답 등을 모의 구현한다. 따라서 테스트 통과는 수집·상태·복원 규칙의 회귀 검증이지, 실제 사이트의 최신 DOM·브라우저 레이아웃·번역 품질·GPU 성능까지 검증했다는 의미가 아니다. 이 리뷰 자료를 작성하면서 새 실사이트 동작 검증이나 번역 품질 측정은 수행하지 않았다.

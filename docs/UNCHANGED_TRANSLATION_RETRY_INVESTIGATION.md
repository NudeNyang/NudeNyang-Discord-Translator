# 원문과 같은 번역 결과의 반복 요청 조사

조사 대상은 0.7.7-beta 공개본과 파일 내용이 같은 `e816a49`이다. 아래 재현 결과는 수정 전 기록이며, 후속 수정 내용은 마지막 절에 정리했다.

## 확인한 문제

외부 번역기가 원문과 같은 내용을 반환하고 품질 검사가 이를 거절하면, 화면에 남아 있는 같은 메시지를 계속 요청한다. 한 함수가 무한 재귀하는 문제가 아니라 **실패 → 다음 화면 수집 → 새 요청**이 반복되는 문제다. 화면 수집 사이클을 아우르는 메시지별 재시도 상한이나 실패 대기 시간이 없다.

1. `translation/resilient.rs`의 `translation_needs_repair`는 원문과 결과를 정규화해 비교한다. 영어 코드처럼 그대로 유지해야 할 내용도 길이·문자 조건에 따라 거절한다.
2. `ResilientTranslator::translate_many`는 처음 받은 결과가 부적합하면 줄 단위로 다시 요청한다. 단일 행도 다시 요청한다.
3. `translation/service.rs`의 `translate_many_unchunked`는 보완 결과도 부적합하면 `번역 품질 검사 실패`를 반환한다. 이 결과는 정상 번역 캐시에 저장하지 않는다.
4. `engine.rs`의 `drain_worker_results`는 대기 목록에서 요청을 제거한다. 성공한 결과에만 `PartState`를 기록하고 오류는 알림에만 남긴다.
5. 다음 `plan_dom_updates`에서 같은 원문은 처리 기록도 대기 기록도 없으므로 다시 큐에 들어간다. 기본 화면 수집은 초당 8회다. 실제 요청 속도는 API 응답 시간 등의 영향을 받는다.

`make_translator`에서 OpenAI 호환 API·DeepL·ChatGPT·Claude·Gemini 모두 같은 보완 래퍼를 사용한다. 이 외부 공급자들은 `isolate_incoming_failures` 기본값 `false`를 사용한다. 로컬 Hy-MT 계열은 `true`를 사용하므로 한 처리 사이클에서는 제한된 재시도 뒤 원문을 반환한다. 따라서 모든 공급자가 똑같이 무한 반복한다고 단정할 수는 없다. 원문 유지 결과의 화면 재생 캐시 제외 때문에 화면을 벗어났다 돌아올 때 재호출되는 문제도 별도 검토 대상이다.

## 재현 결과

격리된 Chromium 화면에 합성 Discord 메시지를 만들고, 실제 Rust 컨트롤러·DOM 수집·작업 큐·OpenAI 호환 HTTP 공급자를 실행했다. 127.0.0.1 모사 API는 항상 HTTP 200과 올바른 JSON을 반환하며 요청받은 텍스트를 그대로 돌려준다. 응답마다 40ms를 기다렸다. 인증 헤더가 전송되지 않았음을 검사했다. 실제 Discord 대화나 유료 API를 사용하지 않았다.

각 표본은 화면 활성화 후 1.8초씩 두 번 관찰했다. 완료 전의 요청도 서버에 도착하면 집계하므로 시간과 횟수는 성능 보장 수치가 아니다.

| 표본 | 앞 1.8초 | 뒤 1.8초 | 합계 |
| --- | ---: | ---: | ---: |
| 일반 텍스트 `while(true)` | 26 | 29 | 55 |
| 영어 일반 문장을 그대로 반환 | 28 | 29 | 57 |
| 일반 텍스트 `Ctrl + Alt + Del` | 0 | 0 | 0 |
| 일반 텍스트 `#include <stdio.h>` | 0 | 0 | 0 |
| 일반 텍스트 `print("1")` | 0 | 0 | 0 |
| `<pre><code>` 안의 `print("1")`와 `while(true)` | 0 | 0 | 0 |

영어 문장을 먼저 정상 번역한 뒤 같은 메시지 위치를 단축키·include·print 표본으로 바꾼 세 경우도 각각 0회였다. 언어 감지와 수집 조건 때문에 제보의 모든 예제가 항상 요청되는 것은 아니다. 실제 `code`·`pre` 요소는 DOM 수집에서 제외한다. 일반 텍스트 코드나 다른 DOM 구조까지 모두 제외한다고 보장하지는 않는다.

반복한 두 표본은 모두 `번역 품질 검사 실패: 결과가 원문을 충분히 번역하지 못했습니다.` 알림을 남겼다. 뒤 관찰 구간에서도 요청이 증가했고, 코드에서 전체 사이클의 상한이 없음을 확인했다. 실제로 수만 번 요청됐는지, 유료 서비스에서 얼마가 청구됐는지는 조사하지 않았다. DeepL·구독 CLI의 실제 계정 호출도 하지 않았으며 해당 공급자의 영향은 공통 경로 분석에 근거한다.

## 권장 수정

- 메시지·원문·공급자 설정별로 전체 재시도 횟수를 제한한다. 한도를 소진하면 원문 유지 상태를 기록해 다음 화면 수집에서 즉시 다시 요청하지 않도록 한다. 원문 수정, 공급자 변경, 사용자 재시도 시에만 이 상태를 적절히 해제한다.
- 결과가 원문과 같다는 이유만으로 계속 실패시키지 않는다. 코드·단축키·고유명사 등 정상적인 원문 유지와 번역 실패를 구분하고, 품질 검사를 포기하더라도 원문을 안전하게 보여주는 종료 경로를 둔다.
- 네트워크 오류나 요청 제한은 원문 동일 판정과 구분하고 대기 시간과 상한을 적용한다. 한 항목 때문에 성공한 다른 항목까지 반복 호출하지 않도록 검사한다.
- 설정 스위치는 보조 수단이다. 스위치 상태와 관계없이 무제한 반복을 막는 것이 먼저다. 추가한다면 부정형인 ‘번역되지 않은 결과 거부’보다는 ‘원문과 같은 결과 재시도’처럼 동작을 직접 설명하는 문구가 낫다.

## 다시 실행하기

Windows 개발 환경에서 저장소 루트를 작업 폴더로 사용한다.

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = '0'
npx playwright test --config scripts/diagnostics/unchanged-retry.playwright.config.mjs
```

`extension/e2e/discord-retry.spec.mjs`의 회귀 검사 4개를 실행한다. 첫 검사는 9개 표본의 요청 횟수를 `UNCHANGED_RETRY_PROBE` JSON으로 출력하며, 원문 반환이 품질 검사에서 거절되는 두 표본은 총 2회, 뒤 관찰 구간에서는 추가 요청 0회를 요구한다. 나머지 검사는 DOM 재생성·원문 편집·번역 스위치 재시도·다른 메시지 처리와 서버 오류의 대기·종료·복구를 확인한다. `npm run test:e2e` 전체 검사에도 포함된다.

## 후속 수정

Discord 화면 수집과 번역 워커가 같은 실패 기록을 확인한다. 품질 보완까지 실패한 메시지는 원문을 그대로 두고 자동 요청을 중단한다. 품질 검사 자체나 코드·멘션·URL 보호 규칙은 바꾸지 않았다.

그 밖의 오류는 첫 실패 후 2초, 두 번째 실패 후 4초 기다리고 최대 3번의 처리 사이클에서 종료한다. 이 상한은 워커 사이클 기준이다. 긴 메시지의 분할 번역이나 공급자 내부 보완 호출까지 모두 합친 HTTP 요청 수 상한은 아니다. 성공하면 해당 실패 기록을 제거한다.

실패 키에는 공급자 namespace, 번역 세대, 채널, 메시지 문맥, 원문 조각, 대상 언어와 원문 언어 필터를 포함한다. DOM 노드만 재생성되어도 실패 기록을 재사용한다. 원문을 수정하거나 번역을 껐다 켜거나 모델·언어 설정을 변경하면 새로 처리할 수 있다. 번역 기록 삭제와 공급자 재활성화도 실패 기록을 비운다. 실패 기록은 최대 1,024개를 메모리에만 보관하며 정상 번역 캐시나 SQLite에 원문 유지 결과를 저장하지 않는다. 앱을 다시 시작하거나 한도 때문에 오래된 기록이 밀려나면 해당 메시지가 다시 시도될 수 있다.

수정 전 회귀 검사는 `while(true)`의 3.6초 관찰에서 51회 요청되어 실패했다(기대 상한 2회). 같은 검사에 수정 코드를 적용한 뒤 2회에서 멈췄다. 실제 Rust 컨트롤러와 OpenAI 호환 HTTP 경로를 사용하되, 화면과 서버는 합성 fixture다. 실제 로그인 Discord, 유료 API, 구독 CLI 계정으로 요청 횟수를 측정한 것은 아니다. 이번 수정 범위는 Discord 수신 메시지의 오류 재등록이며, 로컬 번역기가 성공으로 반환하는 원문 유지 결과의 재마운트 처리와 웹·보내는 메시지·이미지 경로의 정책은 그대로다.

## 수정 검증 기록

- `cargo test --manifest-path src-tauri/Cargo.toml`: 513개 통과, 50개 명시적 제외.
- `npm test`: 790개 통과(웹 274, 랜딩 38, 확장 469, 사전 9).
- `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`, `git diff --check`: 통과.
- `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/package_windows_variants.ps1`: x64·ARM64 릴리스 빌드와 설치 파일 생성 통과. 로컬 개발자 실행본용이며 공개 0.7.7-beta 릴리스 자산과 업데이트 목록은 변경하지 않았다.
- 첫 `npm run test:e2e`: 202개 통과, 기존 Outlook 재표시 검사 1개 실패. 재표시 뒤 요청이 1회에서 2회로 늘었다. 해당 검사는 Rust 본체 대신 모사 Native Messaging을 사용하며 이번 변경 파일을 실행하지 않는다. Outlook 검사 3개를 각각 3번 실행한 `npm run test:e2e -- compatibility.spec.mjs --grep '메일 읽기 outlook' --repeat-each 3`에서는 9개 모두 통과했다. 최초 실패 원인은 확정하지 않았으며 관련 제품 코드나 기대값을 바꾸지 않았다.
- 최종 `npm run test:e2e` 재실행: 203개 모두 통과(4.9분). 새 재시도 회귀 검사 4개와 기존 Discord·확장 검사를 포함한다.

# 0.7.9-beta Discord 연결 상태 표시 조사

조사일: 2026-09-30. 앱 설정을 보는 동안 파이프가 연결되어 있는데도
상단에 `연결 확인 필요`가 표시된다는 보고를 확인했다. 아래는 수정 전 조사 기록이며,
0.7.10-beta에 반영한 수정은 문서 끝에 정리했다.

## 확인한 동작

Discord가 아닌 창을 사용하는 것만으로 연결 오류가 생겨서는 안 된다.
[활성 창 번역](DISCORD_ACTIVE_WINDOW.md)의 설계대로 수집과 결과 적용을 멈추고,
기존 연결과 번역을 유지하면서 `Discord 창 대기 중`을 표시하는 것이 정상이다.

조사 당시 실행 중인 0.7.9-beta의 인증된 로컬 브리지에서도 `discordConnected: true`를
확인했다. 이 조회는 현재 연결 상태만 보여 주므로, 스크린샷 촬영 당시의 오류 문자열까지
소급해서 확인한 것은 아니다. 대신 아래의 격리 재현에서 같은 화면 표시 조건을 확인했다.

## 재현

기존 Discord E2E fixture에 테스트용 `replace` 명령을 임시로 추가했다.
운영 코드의 `RustEngine::replace_cdp`를 호출하고, 연결 성공 후 상태를 조회하는 명령이다.
프로세스 탐색과 창 활성 상태, 번역 모델은 모사했으며 Rust 컨트롤러와 CDP 통신,
브라우저 문서, 상태 문구 함수는 실제 코드를 사용했다. 실제 Discord 대화와 유료 번역
서비스를 대상으로 실행한 검사는 아니다.

1. 접근할 수 없는 fixture 주소로 연결을 시도하여 오류를 만든다.
2. Discord가 아닌 창을 활성화한다.
3. 같은 Discord PID에 정상 CDP 연결을 전달한다.
4. 연결과 비활성 창 상태, 오류 문자열, 화면 문구를 확인한다.

```json
{
  "connected": true,
  "waiting": true,
  "foreground": false,
  "issue": "Discord 보안 연결이 필요합니다. 해당 Discord 앱을 다시 시작하십시오.",
  "label": "연결 확인 필요"
}
```

Discord 창으로 돌아가면 런타임에 표시되는 오류가 비워졌다. 다른 창으로 다시 이동하면
같은 오류가 되살아났으며, 그때도 `connected`는 `true`였다.
오류 없이 연결한 별도 fixture에서는 다른 창으로 이동해도 연결을 유지하고
`Discord 창 대기 중`을 표시했다. 창 전환 자체가 연결을 끊는 현상은 재현되지 않았다.

## 원인

- `src-tauri/src/engine.rs`의 `Control::ReplaceCdp` 성공 경로는 새 연결을 저장하면서
  `session.connection_issue`를 비우지 않는다. 이전 연결 실패가 남아 있으면 정상 연결과
  오류 문자열이 동시에 존재할 수 있다.
- 활성 창에서 연결을 확인하는 경로는 `runtime.connection_issue`만 비운다.
  다음 상태 갱신에서 세션의 이전 오류를 다시 복사하며, 비활성 창에서는 연결 확인
  경로를 실행하지 않아 그 오류가 계속 표시된다.
- `web/state.mjs`의 `discordConnectionLabel`은 연결 여부를 확인하기 전에 오류 문자열을
  검사한다. `web/app.js`의 상태 점 색상도 연결 여부와 관계없이 같은 문자열을 오류로
  처리한다. 따라서 연결이 정상인 상태에서도 경고 문구와 빨간 점이 나타난다.

9월 6일 활성 창 지원 커밋 `6ec4e2d` 이전에는 `cdpConnected`를 먼저 확인하여
연결된 상태를 우선 표시했다. 해당 커밋에서 창 대기 상태를 추가하면서 오류 문자열이
연결됨보다 우선되었고, 오류를 보관하는 세션 상태도 도입되었다.
0.7.8-beta와 0.7.9-beta에도 같은 조건이 남아 있으며, PR #4의 변경으로 생긴 문제는 아니다.

## 수정할 범위

검증된 새 연결을 전달하거나 기존 연결 확인에 성공했을 때 세션과 런타임의 이전 연결
오류를 함께 지워야 한다. 화면에서도 연결이 유지되는 동안 이전 연결 오류만으로
경고 문구와 빨간 점을 표시하지 않도록 문구와 색상 조건을 맞춰야 한다.

실제 연결이 끊어졌거나 Discord 추가 인증 때문에 연결을 중지한 경우에는 해당 안내를
유지해야 한다. 창이 비활성이라는 이유만으로 모든 오류를 숨기는 변경은 적절하지 않다.

## 실행한 검사

- `node --test web/test/state.test.mjs`: 기존 상태 검사 23개 통과.
- `npm run test:e2e -- investigation-discord-status.spec.mjs discord-focus.spec.mjs --grep 'investigation:|three releases follow focus' --workers=1`:
  조사용 재현 2개와 기존 세 배포판 창 전환 검사 1개, 총 3개 통과.
  조사용 검사는 오류가 남는 현재 동작을 확인한 것이며 수정 검증이 아니다.
- 테스트 전용 드라이버 변경과 임시 spec은 실행 후 제거하고 원본 파일 해시를 확인했다.

조사 단계에서는 앱 소스, 설정, 실행 파일과 바로가기를 변경하지 않았으며,
전체 E2E와 설치형 패키징을 실행하지 않았다.

## 0.7.10-beta 수정

재연결과 활성 연결 확인에 성공하면 세션에 보관한 이전 오류를 비운다. 재연결 성공 결과를
돌려주기 전에 런타임 연결 상태도 함께 갱신한다. 연결된 상태에서는 이전 연결 오류만으로
경고 문구나 빨간 점을 표시하지 않으며, 비활성 창에서는 기존 `Discord 창 대기 중`을 사용한다.

재연결에 실패한 경우에는 새 오류를 세션에도 저장하여 비활성 창의 다음 상태 갱신에서
사라지지 않도록 했다. 추가 인증과 번역 모델 오류 안내는 유지한다.

수정 전에 상태 문구 검사, 설정 화면의 상태 점 검사, Rust 컨트롤러의 재연결 성공·실패
검사가 각각 실패했다. 정상 연결 뒤 남은 오류, 잘못된 빨간 점, 실제 실패 오류가 사라지는
상황을 모두 확인한 뒤 수정했다. 재연결 검사는 상시 E2E로 보존한다.

동작 수정 후 `npm run test:e2e` 전체 205개, Rust 검사 517개(환경이 필요한 50개 제외),
`npm test` 791개와 설정 화면 E2E 10개가 통과했다. 창 전환 후 오류가 다시 나타나지 않는
경우와 실제 연결 실패 안내가 유지되는 경우를 함께 검사했다.

0.7.10-beta 버전 동기화 뒤 Rust 517개, 웹 275개, 설정 화면 E2E 10개와
재연결 성공·실패 E2E 2개를 다시 실행하여 통과했다. 포맷 검사와 인터페이스
695개 문구·28개 언어 검사도 통과했다.

검증은 격리 문서와 모사한 OS 상태·번역 모델을 사용한다. 실제 로그인된 Discord 대화,
메시지 전송, ARM64 장치 실행을 검증한 것으로 해석하지 않는다.

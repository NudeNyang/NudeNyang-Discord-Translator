# CPU 스레드 수 재검증 — 0.7.6-beta 개발자판

## 기존 제한을 넣은 이유

`b241ba34d79617aa6b0be47a0553c4dd83e2b46c`(2026-09-05,
`CPU 번역 계산량 제한과 Discord 연결 감시 최적화`)에서 CPU 실행에
`clamp(logical_cpus / 2, 1, 6)`을 도입했다. 게임 실행 중 느려짐을 조사하면서
추론 스레드 수뿐 아니라 busy polling 비활성화와 낮은 우선순위도 함께 적용했다.

당시 기록은 [CPU 성능 검증](CPU_PERFORMANCE.md)에 있으며 원시 결과도 로컬
`artifacts/cpu-translation-confirmation.json`, `artifacts/cpu-translation-long.json`에 남아 있다.
짧은 표본에서 기존 기본 설정과 6스레드는 각각 평균 1.212초와 1.205초였고,
모델 프로세스 CPU 사용률은 47.26%와 18.40%였다. 긴 표본에서도 각각
5.496초와 5.349초로, 번역 시간을 거의 유지하면서 CPU 사용량을 줄인 결정이었다.

다만 당시 비교는 스레드 수·polling·우선순위를 함께 바꾼 설정 전체의 비교다.
CPU 약 61% 감소를 스레드 상한 하나만의 효과로 해석하지 않는다. 게임 FPS나
프레임 시간은 측정하지 않았으며, 모든 CPU·모델에서 6스레드가 최적이라는 근거도 아니다.

## 이번 비교 방법

- CPU: AMD Ryzen 9 9950X3D, 물리 16코어·논리 프로세서 32개.
- 앱 버전: `0.7.6-beta`; 현재 패키징된 실제 `llama-server.exe` 사용.
- 모델: Hy-MT2 1.8B Q4_K_M. 모델 SHA-256은
  `dc5f44fcf1fa496ee7ad725982c0c8c553a4de00259b53af84c4b89fb0c06699`.
- 실행기 SHA-256은
  `4deca4ce412c51d89eb9712377e8f31b7739724c374e78e8cbb8ca94b4e01526`.
- `--threads`와 `--threads-batch`를 각각 6·16·32로 설정했다.
  GPU 사용 안 함, context 2048, parallel 1, poll/poll-batch 0, priority -1은 동일하다.
  32는 논리 프로세서 수만큼의 추론 작업 스레드를 허용하는 조건이며,
  CPU 사용률을 100%로 강제하거나 CPU affinity를 고정하는 조건은 아니다.
- 번역기 본체와 그 소유 모델만 잠시 종료하고 독립 서버를 하나씩 실행했다.
  다른 사용자 앱을 종료하거나 설정을 바꾸지 않았으며, 측정과 빌드·테스트를 겹치지 않았다.
- 기존 `scripts/benchmark-cpu-translation.ps1`의 합성 영어 → 한국어 표본을 사용했다.
  temperature 0, seed 42, max_tokens 256, prompt cache 비활성화이며
  각 새 서버의 첫 예열 요청은 집계에서 제외했다.
- 짧은 문장/문단 3종은 서버당 2회씩, 긴 문단 1종은 2회씩 측정했다.
  6→16→32 순서 뒤 32→16→6 순서로 반복해, 스레드 설정별 짧은 요청 12개와
  긴 요청 4개, 전체 측정 요청 48개를 비교했다.
- CPU 사용률은 모델 프로세스의 CPU 시간 증가량을 요청 경과 시간과 논리 프로세서
  32개로 나눈 값이다. 작업 관리자에 보이는 PC 전체 사용률과 구분한다.

재현 시 앱을 종료한 뒤 다음 명령을 순방향과 역방향으로 각각 실행한다.
실행기와 모델 경로는 현재 설치 경로를 명시한다.

```powershell
foreach ($order in @('forward','reverse')) {
    $profiles = if ($order -eq 'forward') { @('6','16','32') } else { @('32','16','6') }
    foreach ($profile in $profiles) {
        ./scripts/benchmark-cpu-translation.ps1 -ServerPath <llama-server.exe> -ModelPath <model.gguf> -Profiles @($profile) -Rounds 2 -OutputPath "artifacts/cpu-20260911-$order-$profile-short.json"
        ./scripts/benchmark-cpu-translation.ps1 -ServerPath <llama-server.exe> -ModelPath <model.gguf> -Profiles @($profile) -Rounds 2 -LongText -OutputPath "artifacts/cpu-20260911-$order-$profile-long.json"
    }
}
```

실제 측정은 각 순서 안에서 설정별 short→long을 실행했고, 파일은
`artifacts/cpu-20260911-{forward|reverse}-{6|16|32}-{short|long}.json`으로 분리했다.
실행 래퍼, 머신 정보와 집계 스크립트는 같은 접두어의 로컬 artifacts에 보관한다.
로그와 원시 결과는 Git에 추가하지 않는다.

## 실측 결과

| 추론 스레드 | 짧은 문장/문단 평균 | 긴 문단 평균 | 짧은 표본 모델 CPU | 긴 표본 모델 CPU |
| --- | ---: | ---: | ---: | ---: |
| 6 (현재) | 1.198초 | 5.183초 | 18.55% | 18.51% |
| 16 (물리 코어 수) | 1.278초 | 5.583초 | 46.79% | 46.78% |
| 32 (논리 프로세서 수) | 1.923초 | 9.447초 | 60.80% | 60.09% |

표는 요청별 산술 평균이다. 시간으로 가중한 모델 CPU 사용률도 집계했으며,
짧은 표본은 18.54%/46.72%/60.33%, 긴 표본은 18.51%/46.78%/59.86%였다.
48개 요청 모두 정상 종료(`finish_reason=stop`)했고, 원문 표본별 번역 결과는
스레드 수·실행 순서·반복에 관계없이 완전히 동일했다.

순서별 평균도 같은 경향이었다.

| 스레드 | 순방향 짧은/긴 표본 | 역방향 짧은/긴 표본 |
| --- | ---: | ---: |
| 6 | 1.259초 / 5.326초 | 1.138초 / 5.041초 |
| 16 | 1.223초 / 5.551초 | 1.333초 / 5.614초 |
| 32 | 1.906초 / 9.972초 | 1.941초 / 8.921초 |

32스레드는 6스레드보다 짧은 표본에서 약 61%, 긴 표본에서 약 82% 오래 걸렸다.
16스레드도 합산 평균에서 개선되지 않았다. 작은 차이는 배경 부하 등으로 달라질 수 있지만,
이번 비교에는 모든 논리 스레드를 기본으로 사용할 성능상 근거가 없다.

## 판단과 검증 범위

현재 6스레드 정책을 유지한다. 기존 제한에는 실측 근거가 있었고, 이번 사용자 PC의
현재 기본 모델 비교에서도 최대 스레드 사용이 오히려 느렸다. `0.7.6-beta`의
[캐시 복원·가시 작업 정리](DISCORD_SCROLL_PERFORMANCE.md)는 별도 지연 원인을
해결한 변경이므로 함께 유지한다.

많은 스레드가 항상 빠르지 않다는 현상은 측정했지만, 메모리 대역폭·코어 간 통신·
동기화·OS 스케줄링 중 어느 요소가 얼마만큼 원인인지는 하드웨어 카운터로 분석하지 않았다.
32스레드에서도 모델 CPU 사용률이 약 60%인 것을 자원이 부족하지 않다거나 더 강제로
CPU를 사용하면 빨라진다는 증거로 해석하지 않는다. priority와 polling은 통제 변수로
유지했으며, 우선순위 상승·busy polling 재활성화 효과까지 검증한 비교는 아니다.

현재 PC·Hy-MT2 1.8B·고정 합성 표본에서 얻은 결과다. 친구의 5950X, 다른 모델,
게임 FPS, 실제 Discord DOM 표시 지연, 장시간 열/전력 변화는 이번 비교에 포함되지 않는다.
자동 스레드 튜닝이나 사용자 선택 기능도 추가하지 않는다.

측정 후 기존 바로가기로 개발자판을 다시 실행했고, 실행 파일 경로와 제품 버전
`0.7.6-beta`, 본체 자식 모델의 `--threads 6 --threads-batch 6`을 확인했다.
바로가기의 대상·작업 폴더·아이콘도 기존 개발자 실행본과 일치했다.
제품 코드·설정·버전·실행 파일을 바꾸지 않은 조사이므로 새 빌드·패키징이나 전체 E2E는
반복하지 않았다. 실제 모델 벤치마크, 48개 결과의 개수·정상 종료·동일 출력 검사와
문서 diff 검사를 수행했다. 공개 배포·푸시·업데이트 목록 변경은 없다.

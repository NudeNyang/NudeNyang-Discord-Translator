# 전송 통역의 기호 입력 통과 — 0.7.6-beta

## 원인과 변경 이력

`!?` 같은 입력을 번역에서 제외하는 Rust 규칙은 삭제되지 않았다.
`outgoing_can_passthrough("!?", None)`도 참이며, 번역 서비스 자체도
번역 가능한 내용이 없는 입력을 모델에 보내지 않는다.

문제는 전송 입력창의 비동기 사전 판정과 Enter 처리 사이의 경쟁이었다.
`queueDraftCheck()`는 `classify`를 보내고, Rust 결과가 돌아오면
`draftDecision.resolved && draftDecision.pass`가 되어 원래 Enter를 통과시킨다.
입력 직후 Enter를 누르면 아직 판정이 없어 Enter를 차단하고 `translate` 요청을 만들었다.
명시적 전송 언어에서는 불필요한 번역 대기·검토 경로로 들어갈 수 있었고,
자동 언어에 최근 대화 근거가 없으면 기호뿐인데도 언어 감지 실패 안내를 표시할 수 있었다.
이는 모델이 실제로 기호를 번역하도록 호출됐다는 의미와는 구분한다.

- `0a23942`(2026-08-22)는 자동 전송을 제거하고 검토 후 사용자의 Enter로 전송하도록 변경했다.
- `90be060`(2026-08-23, 닉네임 보존과 전송 원문 통과 지원)은 비동기 입력 판정과
  판정 완료 시 Enter 통과를 추가했다. 판정 전 Enter에 대한 기호 입력 예외는 없었다.
- 이 조건은 최신 코드에도 그대로 남아 있었다. `4a10f52`의 0.7.6 스크롤·캐시 수정이나
  `dce97dd`의 CPU 조사에서 기호 제외 규칙을 삭제한 회귀는 아니다.

## 수정

입력창에서 번역 대상 꼬리 문장에 Unicode 문자 또는 숫자(`\p{L}`, `\p{N}`)가
하나도 없으면 언어 판정을 요청하지 않고, Enter에서도 즉시 같은 기준을 확인한다.
`!?`, 전각 문장부호, 수학·화살표 기호, 이모지와 공백 조합은 원래 Enter를 통과시킨다.
`왜!?`, `Really!?`, `何！？`, 한 글자와 숫자가 포함된 입력은 기존 언어 판정을 유지한다.
URL·멘션·문자 이모티콘 등 더 복잡한 보호 규칙은 기존 Rust 판정을 그대로 사용한다.

지원하는 네이티브 앞쪽 멘션은 그대로 두고 그 뒤의 문장만 확인한다.
같은 입력창의 이전 미완료 요청은 기호 입력을 통과시킬 때 취소하여 늦은 검토 결과를
삽입하지 못하게 한다. 취소된 요청의 늦은 실패 안내도 표시하지 않으며,
현재 유효한 요청의 오류 안내는 유지한다. 검토문 삽입 중 Enter 보호, 자동완성·IME·수정자 키 처리와
사용자가 검토한 번역문의 Enter 전송은 기존 순서를 유지한다.

전송 키를 새로 만들거나 메시지를 자동 전송하지 않는다. 기존 사용자 키 이벤트에
`preventDefault()`를 하지 않는 처리다. 앱 버전은 `0.7.6-beta`로 유지하고,
이미 연결된 Discord의 이전 핸들러를 교체하도록 주입 컨트롤러 버전만 63→64로 올렸다.

## 재현과 검증

`extension/e2e/discord-focus.spec.mjs`는 실제 Rust 컨트롤러와 CDP 연결을 사용하되,
Discord 페이지·네이티브 프로세스 발견·번역 모델은 격리된 표본과 모사 모델을 사용한다.
입력과 Enter를 같은 JavaScript 작업에서 실행하여 Rust 판정이 먼저 도착할 수 없게 했다.

수정 전 `outgoing punctuation bypasses Enter interception before draft classification returns`는
`!?`에서 실패했다. 예상은 `prevented:false, pending:0, queued:[]`였지만 실제는
`prevented:true, pending:1, queued:["classify","translate"]`였다.
수정 뒤 이 재현과 다음 경계 검사 모두 통과했다.

- 자동 언어·대화 근거 없음·여러 종류의 기호 입력에서도 원문과 Enter를 유지한다.
- 문장부호와 일반 글자가 섞이면 기존 번역 요청을 만든다.
- 네이티브 앞쪽 멘션을 보존하고, 이전 요청을 지워 늦은 검토 삽입을 거절한다.
- 이전 요청 취소 후 늦은 오류 안내가 표시되는 추가 재현도 수정 전에 실패했다
  (`lateErrorVisible:true`). 요청 존재 여부를 확인하여 늦은 오류는 무시하고,
  유효한 현재 요청의 실패 안내는 표시하는 경계를 함께 검사한다.
- Rust 서비스 검사에서 수신·전송 경로 모두 기호 입력을 그대로 반환하고
  한국어·영어·일본어 전송 대상에서 번역 제공자 호출이 없는지 확인한다.

실제 로그인 Discord에 메시지를 보내거나 개인 입력 내용을 읽지 않았다.
실제 Discord에서 물리 Enter로 전송하는 확인은 이 격리 E2E와 별도다.

전체 검증 기록:

- `npm test`: 785개 통과(웹 269, 랜딩 38, 확장 469, 스크립트 9), 사전 팩 검사 통과.
- `npm run test:e2e`: 최종 소스에서 전체 189개 통과, 4.7분. 신규 재현·경계 검사 3개를 포함한다.
- `npm run test:locales`, `cargo fmt --manifest-path src-tauri/Cargo.toml -- --check` 통과.
- 첫 Rust 전체 검사는 사용자 기본 데이터 경로에서 기존 private browser 테스트 2개가
  실패한 뒤 `fatal runtime error: I/O error: operation failed to complete synchronously`
  및 `0xc0000409`로 중단됐다. 실패 테스트를 단독 실행했을 때에도 mock 번역기 준비가
  6초 내 완료되지 않았다. 같은 바이너리에서 `LOCALAPPDATA`와 `DISCORD_TRANSLATE_CONFIG`를
  별도 테스트 폴더로 지정하자 해당 단독 검사가 0.18초에 통과했다.
  기본 데이터 환경의 준비 지연과 뒤따른 입출력 중단의 내부 원인까지 확정한 것은 아니다.
  사용자 데이터는 삭제하거나 테스트용으로 초기화하지 않았다.
- 데이터 경로를 격리한 상태에서 `cargo test --manifest-path src-tauri/Cargo.toml -- --test-threads=1`을
  최종 소스를 전체 재실행하여 493개 통과, 0개 실패, 기존 50개 무시를 확인했다(194.63초).
- 공통 웹 DOM 수집·가시성·적용 코드는 변경하지 않았으므로 외부 공개 표본 검사는
  다시 실행하지 않았다. 전체 E2E의 기존 웹·메신저 보호와 문단 보존 검사는 포함했다.

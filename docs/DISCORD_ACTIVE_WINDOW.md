# Discord 활성 창 번역

## 사용자 동작

- 기존 Discord 선택 항목의 기본 자동 모드는 `자동 · 사용 중인 창`이다. 별도 탭이나 배포판별 스위치를 추가하지 않는다.
- Stable·PTB·Canary를 함께 실행하고 클릭 또는 Alt+Tab으로 사용할 창을 선택한다. 마지막 실행 시각으로 대상을 정하지 않는다.
- 받은 메시지 번역, 보내는 메시지 통역, 모델과 언어 설정은 전역으로 공유한다.
- 다른 프로그램을 사용하는 동안 새 메시지 수집과 번역 결과 적용을 멈춘다. 이미 적용된 번역은 유지한다.
- 실시간 번역을 끄면 연결된 세 배포판의 원문을 모두 복구한다. 다시 켜면 활성 Discord부터 번역한다.
- 보내는 메시지의 결과는 요청한 작성창으로 돌아온 뒤에만 적용한다. 다른 배포판의 초안을 덮어쓰지 않는다.
- 상태 표시줄과 트레이에는 마지막으로 선택한 배포판을 표시한다. 특정 배포판 고정 선택도 유지한다.
- 자동 모드는 실행하지 않은 Discord를 임의로 시작하지 않는다. 앱 자동 시작이 켜져 있으면 사용자가 Windows 자동 시작에 등록했던 배포판만 보안 파이프로 시작한다. 이미 일반 모드로 실행 중인 창의 최초 보안 연결에는 기존 안내·동의·재시작 절차를 사용한다.

## 구현 경계

`discord_focus.rs`는 Windows 전경 HWND의 PID를 확인한다. `discord.rs`는 실행 파일 경로가
확인된 Discord 프로세스와 대응시킨다. 컨트롤러는 배포판별 연결, DOM 원문, 작업 세대,
화면 세대, 이미지·작성창 요청과 인증 중지 상태를 보존한다. 로컬 모델과 번역 워커는 공유한다.

작업 세대 상위 비트로 배포판을 구분하고, 대기 작업 제거도 배포판별로 수행한다. 이전의
단일 최대 세대 비교는 다른 배포판의 유효 작업을 버렸으므로 제거했다. 전경 PID를 다시
확인하고 CDP의 `document.hasFocus()`까지 확인한 후에만 수집·결과 적용을 허용한다.
동일 프로세스의 보조 창이 활성화되어 기본 채팅 문서에 포커스가 없으면 수집하지 않는다.

비활성 연결에는 메시지 수집 없이 컨트롤 상태와 생존 신호만 전달한다. 전역 OFF·앱 종료는
모든 연결을 정리한다. 재시작에는 요청 당시 PID를 전달하며, 인증용 재시작도 현재 활성
세션 대신 요청한 배포판의 세션을 중지한다. 추가 인증 중지는 배포판별로 저장한다.

## 검증 방법

`npm run test:e2e`는 전체 브라우저 E2E를 실행한다. `discord-focus.spec.mjs`는 실제
Rust 컨트롤러·CDP·주입 스크립트·워커를 사용하고, OS 프로세스/포커스 관찰과 번역 모델만
대체한다. Chromium은 격리 프로필과 로컬 테스트 문서를 사용한다.

- 세 배포판 전환, 비활성 창의 기존 번역 유지, 비활성 새 메시지 제외
- 렌더러 생존 검사 시간을 넘긴 대기 후 유지 및 전역 OFF 원문 복구
- 한 배포판의 추가 인증·연결 종료가 다른 배포판에 영향을 주지 않음
- 배포판 고정 선택과 자동 모드 복귀
- 지연된 보내기 번역의 원래 작성창 적용 및 다른 초안 보존
- 인증 재시작 요청 후 포커스가 바뀌어도 원래 배포판만 중지

마지막 항목은 수정 전 실제 실패를 확인했다. Canary 인증 중지를 요청했지만 활성 Stable이
중지되고 Canary 번역이 남았다. 요청 배포판·PID로 세션을 선택하도록 수정했다.
작업 세대 회귀 테스트도 수정 전 유효 작업 3개 중 1개만 남는 실패를 확인했다.

실제 로그인된 Discord와 로컬 모델 검증은 위 모사 테스트와 별도로 수행한다. 전송 메시지는
실제 서버에 보내지 않으며, 지연 결과·작성창 경계 검증은 격리 E2E로 확인한다. ARM64 설치본
생성과 실제 ARM64 하드웨어 실행 검증도 구분한다.

## 비활성 창의 전송 통역 버튼 깜빡임 수정

다중 연결의 1초 주기 `sync_controls`가 `updateLabel()`만 호출하면서 작성창 없는 채널의
전송 통역 버튼을 다시 표시했다. 활성 창의 수집 경로는 바로 이어서 `reposition()`으로
숨기지만, 비활성 창의 생존 신호 경로에는 이 단계가 없었다. 따라서 상태 갱신과 창 전환에
따라 버튼이 나타났다 사라졌다. 번역 설정 자체가 꺼졌다 켜지는 현상과는 구분된다.

생존 신호에도 기존 `reposition()`을 같은 스크립트 안에서 호출해, 브라우저가 화면을 그리기
전에 작성창 유무·미디어 보기·컨트롤 숨김 규칙을 함께 적용한다. 배경 메시지나 초안 수집은
추가하지 않는다.

`background heartbeats never reveal the outgoing button in a read-only channel` E2E는
작성창 없는 Stable을 연결하고 Canary로 이동한 뒤 여러 생존 신호 동안 버튼의 노출을
20ms 간격으로 검사한다. 수정 전 잘못 노출된 표본이 생겨 실패했고, 수정 후 노출이 0회였다.
정상 작성창의 버튼 표시와 비활성 창에서 작성창이 추가·제거될 때의 표시 변화도 검증한다.

## 기존 사용자의 최초 자동 모드 전환

이 변경을 포함한 버전을 처음 실행하면 기존 설정의 `discord_variant`만 `auto`로 전환한다.
`discord_active_window_setup_version=1`을 함께 저장해 설정창을 열거나 다른 설정을 저장하지
않아도 한 번만 적용된다. 새 사용자는 처음부터 적용 완료 상태로 시작한다. 이후 사용자가
배포판을 직접 지정하면 재실행해도 그 선택을 유지한다. 기존의 독립적인 웹 설정 마이그레이션은
자체 적용 버전으로 계속 관리하며, Discord 전환이 웹 설정을 다시 초기화하지 않는다.

설정 파일 기반 회귀 테스트에서 세 배포판·기존 자동 선택, 전역 번역 스위치·언어·번역기·테마·
단축키·닉네임·웹 번역·인증 중지 상태의 보존, 첫 실행 직후 저장 및 이후 명시적 선택의 보존을
확인한다. 기존 사용자 테스트는 수정 전 자동으로 바뀌지 않아 실패함을 확인했다.

## 재부팅 후 다중 연결·재시작 안내 복구

2026-09-07 실제 재부팅 상태에서 앱 자동 시작 Run 값이 9월 5일 개발 실행본을 가리켰다.
최신 실행본은 별도 `dist` 경로에 있었지만, 기존 자동 시작 검사는 값의 존재만 확인하고
실행 경로를 갱신하지 않았다. 따라서 이전 단일 Discord 엔진이 실행됐으며 Stable만 파이프를
사용하고 PTB·Canary는 일반 시작 명령으로 실행돼 있었다.

최신 브랜치에도 Stable 전용 시작 등록 관리와 자동 모드의 조기 반환이 남아 있었다.
현재는 기존 앱 자동 시작이 활성화된 경우 실행 경로를 따옴표로 감싸 갱신하며, 이미
Discord 파이프가 살아 있어도 등록 동기화를 생략하지 않는다. 자동 시작이 꺼진 사용자를
임의로 등록하지 않으며 Windows의 StartupApproved 값은 갱신하지 않는다.

Discord 시작 명령과 백업은 Stable·PTB·Canary별로 분리한다. 기존 Stable 백업 경로는
이전 버전과의 복원을 위해 유지하고 PTB·Canary 백업에는 배포판 접미사를 사용한다.
자동 모드는 백업된 원래 시작 등록이 있고 Windows에서 사용 중지하지 않은 배포판만
시작한다. 고정 선택은 기존 동작을 유지하며 나머지 배포판의 원래 시작 등록은 복원한다.
앱 자동 시작 해제·제거 시 세 배포판의 등록을 복원하되 사용자가 별도로 수정한 명령은
덮어쓰지 않는다. 인증 중지 중인 배포판은 자동 연결하지 않는다.

이미 일반 모드인 Discord는 강제 종료하지 않고 해당 창 선택 시 기존 재시작 안내로
연결한다. 안내 전에 `main_window_show`를 호출해 트레이에 숨겨진 앱에서도 동의와
카운트다운이 보이게 한다. 요청 당시 PID와 배포판별 재시도 상태는 유지한다.

격리된 HKCU 테스트 키를 사용하는 재현 테스트는 수정 전 `DiscordPTB still starts without
a pipe`로 실패했다. 수정 후 세 등록의 반복 백업과 복원을 검증한다. 실제 안내 함수를
Chromium에서 실행하는 테스트도 수정 전 동의 전에 앱을 표시하지 않아 실패했다.
컨트롤러 E2E는 Stable 연결을 유지한 채 일반 PTB·Canary를 모사해 각각 올바른 PID로
재시작 안내 조건이 성립하는지 검증한다. 이 검증의 Windows 포커스·연결 실패 및 안내의
네이티브 창 호출은 대체되며 실제 OS 재부팅 자체를 수행하는 테스트는 아니다.
